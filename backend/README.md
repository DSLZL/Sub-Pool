# Sub-Pool backend

Go owns authentication and PostgreSQL state, Sub2API connection configuration, local managed accounts, passive quota collection, recorded usage, participants, immutable pool contracts, local observation management, conditional estimate history and protected business backups/restores. The supplied web pages use fixed same-origin Next.js proxies, including backup/restore and personal help reads. Financial operations and other capability-gated behavior remain unavailable until their stated prerequisites are qualified.

Requires Go 1.25 or newer and PostgreSQL. Build from this directory with `go build -o sub-pool ./cmd/sub-pool` (use `sub-pool.exe` on Windows).

## Configuration and startup

Set `SUB_POOL_DATABASE_URL` to a dedicated application database connection string. Supply it through the process environment or your service secret store. Do not put credentials in arguments, source files or logs.

- `SUB_POOL_PUBLIC_ORIGIN`: exact browser origin, for example `https://pool.example.com`; no path, trailing slash, query or credentials.
- `SUB_POOL_LISTEN`: defaults to `127.0.0.1:8081`.
- `SUB_POOL_ALLOW_LOOPBACK_HTTP=true`: explicitly permits an HTTP origin using a loopback IP for local development. Production requires an HTTPS public origin and a reverse proxy providing TLS.
- `SUB_POOL_TRUSTED_PROXY_CIDRS`: optional comma-separated trusted proxy prefixes (at most 32). Empty trusts no forwarded headers. Only a trusted direct peer may supply one valid, bounded `X-Forwarded-For` chain; the service walks it from the right through trusted proxies. Invalid or ambiguous chains fall back to the direct peer. Configure only proxies that sanitize this header and restrict direct access to the backend. The current Next proxy strips forwarding headers, so Go observes its peer address; configuring this variable alone does not identify the browser's IP. Deployment forwarding behavior needs separate verification.
- `SUB_POOL_SECRET_KEY`: base64 encoding of a cryptographically random 32-byte deployment secret, used for AES-256-GCM encryption of upstream management credentials and complete business archive files. Keep the same protected key across restarts. Without it, local authentication and configuration metadata remain usable, but credentials cannot be saved or decrypted. Replacing it cannot decrypt existing credentials; deliberately replace or clear those credentials before using a different key. Do not put the key in source, browser configuration or logs.

Run `sub-pool migrate` to apply embedded SQL migrations. Every command checks migrations; applied files cannot change, unknown newer database versions are rejected, and no command resets an existing database.

Initialize once with `sub-pool bootstrap <username>`, providing the newly chosen password through standard input as UTF-8 without a BOM. Use your deployment secret mechanism or raw stdin redirection; Windows PowerShell string pipelines can add a BOM and are rejected explicitly. There is no default password, public initialization endpoint or credential overwrite. Concurrent requests using different usernames still create only one initial administrator. A disabled existing administrator also prevents reinitialization.

Usernames are trimmed and ASCII-lowercased, then must match `[a-z0-9][a-z0-9._-]{2,63}`. Passwords need ten Unicode characters, an ASCII letter and digit, and at most 128 UTF-8 bytes. Spaces are significant; stdin removes one final line ending. Password hashes use salted PBKDF2-HMAC-SHA256 with 600,000 iterations. Start the service using `sub-pool serve`. Normal startup preserves identities and sessions.

## Web application

Install dependencies once from the repository root with `bun install --frozen-lockfile`. The root workspace contains `web` and the shared `contracts` package; keep the root `bun.lock` as the single lockfile. Run `bun run build` and `bun run start` from `web`.

The Next process needs the same `SUB_POOL_PUBLIC_ORIGIN` as Go, plus `SUB_POOL_BACKEND_ORIGIN` pointing to the fixed Go service origin. For local HTTP use a loopback IP origin and explicitly set `SUB_POOL_ALLOW_LOOPBACK_HTTP=true` on both processes. For example, serve Next on `http://127.0.0.1:3000` and Go on `http://127.0.0.1:8081`. Keep backend origin/configuration server-side. Production needs HTTPS and a deployment-specific reverse proxy check.

The browser holds only an HttpOnly session cookie; local storage preferences cannot grant roles. Protected pages wait for matching current session and access responses. Identity or permission changes clear prior page state; focus and foreground activity recheck the server. Logout revokes the current session. Password changes revoke all sessions and require login again. Requests with uncertain outcomes are not automatically replayed. Business pages remain unavailable until their real modules are connected.

## Authentication API

The versioned oRPC/Zod contract is in `../contracts/auth.ts`. Browser mutations require the exact configured Origin and `application/json`; undeclared/duplicate fields, malformed Unicode, unexpected queries and oversized bodies are rejected. Cookies are HttpOnly, host-only and SameSite=Lax; HTTPS uses a Secure `__Host-sub_pool_session` cookie. Explicit HTTP development uses `sub_pool_dev_session`.

| Endpoint | Input | Result |
| --- | --- | --- |
| POST `/api/v1/auth/login` | `username`, `password` | Current identity and deadlines; sets cookie |
| GET `/api/v1/auth/session` | No query/body | Current stored session; does not extend it |
| POST `/api/v1/auth/renew` | `{}` | Extends idle deadline, bounded by absolute expiry |
| POST `/api/v1/auth/logout` | `{}` | Durable revocation and cookie removal; idempotent |
| POST `/api/v1/auth/password` | `current_password`, `new_password` | Atomic new hash and revocation of all sessions, including caller |

Idle lifetime is eight hours; absolute lifetime is seven days. Disabled identities, revoked sessions and expired sessions are denied using current database state. Login failure limits persist for fifteen minutes: five failures per normalized identifier and twenty-five per server-observed source IP, following the configured trust policy. Responses never include session tokens, hashes or database errors. A network failure after a mutation leaves its outcome unknown; clients must not automatically replay it. Restore/read current state or sign in explicitly as appropriate.

## Users and read permissions

The separate `users-v1` contract is in `../contracts/users.ts`; `createUsersClient` shares the same validated, fixed-origin transport as the auth client. The existing `/users` page uses these endpoints through the Next.js proxy. It reads every backend page before displaying a complete list; a failed page leaves the list unavailable. Create/save and confirmed deletion wait for actual server results. Conflicts keep the dialog open; uncertain writes block repeat submission until a deliberate read, with feedback retained during recovery.

New users start without business grants. Existing scope selectors read complete managed-account and participant catalogs from Go. A failed catalog stays unavailable and preserves stored scope IDs when other settings are saved. Personal machine credentials use the separate API Key boundary below.

| Endpoint | Input | Result |
| --- | --- | --- |
| GET `/api/v1/access` | No query/body | Own current identity, read grants and independent account/participant scopes |
| POST `/api/v1/users/list` | `after` (empty initially), `search` (username prefix), `limit` (1–100) | Ordinary-user summaries and nullable next cursor |
| POST `/api/v1/users/get` | `id` | Ordinary identity, enabled state, version and grants |
| POST `/api/v1/users/create` | `username`, `password`, `enabled`, `features`, `account_ids`, `participant_ids` | Ordinary identity and its initial grants saved atomically |
| POST `/api/v1/users/update` | `id`, `revision`, `username`, `enabled`, `features`, `account_ids`, `participant_ids`, `new_password` (empty means unchanged) | Identity/grants and any credential reset saved atomically with one new revision |
| POST `/api/v1/users/delete` | `id`, `revision`, `confirmation` (exact current username) | Login identity removed; target sessions and API Keys revoked |

All `users/*` actions require a current administrator; they cannot create, promote, edit, reset or delete an administrator. Self access requires a live authenticated session. Every POST requires the exact Origin and JSON; the user boundary rejects duplicate, missing, extra, null or incorrectly typed fields and bodies over 64 KiB. A stale revision returns a defined 409 conflict; read current state before making a deliberate new edit. Failed transport does not establish whether a write committed.

Read features are `overview`, `accounts`, `pools`, `usage`, `observations`, `estimates`, `balances`, `temporary`, `pricing`, `dispatch`, `notifications` and `security`. Each feature is granted at most once. The explicit `security` grant allows global login-audit and source-rule reads; account/participant scopes do not narrow those records. It grants no management-audit read or configuration writes. Account and participant scopes each contain at most 500 unique canonical local IDs (16 random bytes encoded as 22 unpadded base64url characters). They are independent; an unknown ID matches no business facts. Configuration does not prove that an upstream resource exists or a domain capability is available. Profile/password/logout remain personal operations; global settings and management writes are administrator only.

Create/save includes enabled state, grants and credentials in one transaction. Empty initial arrays grant no business access. Lists return grant/scope counts and the latest recorded successful local login time (null when none exists), without returning every user's scope IDs. Permission edits increment the stored revision; new requests read current grants. Disable/reset/delete revoke all sessions and API Keys atomically with the identity change and actor/target audit record. Re-enabling never resurrects revoked credentials. Deletion keeps a disabled tombstone with no password or grants, reserves the username to avoid historical ambiguity, and preserves audit and other business references. It does not remove upstream users, pool participants or their history.

Domain handlers must retain their PostgreSQL transaction through `AuthorizeRead` or `AuthorizeAdmin` and the protected operation. Use `Access.ScopeSQL` with structured `pgx.Identifier` column names and the first bind position to filter SQL before details, search, grouping, pagination or notifications; attribution facts require both scopes and must exclude unknown attribution for ordinary users. Detail checks return the same not-found result for absent and out-of-scope identities. API Key requests reuse these guards and current enabled/revision state. Future endpoints remain closed to machine credentials until explicitly added to the operation catalog.

## Personal and management API Keys

`api-keys-v1` is defined in `../contracts/api-keys.ts` and exported through `createAPIKeysClient`. Users, including administrators, list and manage only their own Keys. Lifecycle POSTs require a live browser session, exact Origin and strict JSON. A Key cannot manage credentials or become a browser session. The existing `/api-keys` page uses this contract through the fixed, session-cookie-only Next proxy.

| Endpoint | Input | Result |
| --- | --- | --- |
| POST `/api/v1/api-keys/list` | `after` (empty initially), `limit` (1–100) | Own metadata, including revoked Keys, and nullable `next_after` |
| POST `/api/v1/api-keys/create` | `name` (1–80 characters, at most 256 UTF-8 bytes, no controls or surrounding whitespace), `mode` (`read` or `management`) | `key` metadata and one-time `secret` |
| POST `/api/v1/api-keys/rotate` | `id`, current `revision` | Same Key ID/mode with a new one-time secret and revision; old secret revoked atomically |
| POST `/api/v1/api-keys/revoke` | `id`, current `revision` | Revoked metadata; a revoked Key cannot be rotated back into service |
| GET `/api/v1/api-keys/access` | No query/body | Current identity, grants and independent scopes; accepts session or machine authentication |
| GET `/api/v1/api-keys/catalog` | No query/body | Current permitted operations, fixed paths/methods, domain contract versions, credential mode, explicit limitations and common error explanations |

Secrets contain a public `spk_live_<local Key ID>_` prefix and 32 cryptographically random bytes. Only their SHA256 digests are stored. List/revoke/catalog never return secrets or hashes; rotation cannot recover a previous secret. Metadata timestamps are UTC, revisions are decimal strings, and unused/never-rotated/not-revoked times are null. `last_used_at` records committed authorized use without changing the lifecycle revision. Rotation resets last use for the new secret. Keys have no automatic expiry in this version. Password change, administrator credential reset, disable and deletion revoke all existing Keys; ordinary grant/scope edits take effect dynamically on the next request. Browser logout leaves independent machine credentials valid until explicitly revoked.

Machine clients send exactly one `Authorization: Bearer <Key>` header and no Cookie, directly to the Go API or a trusted TLS reverse proxy that preserves this header. Machine POST queries require JSON and their existing frozen inputs; an Origin is not required. Cookie POSTs retain exact-Origin protection. Duplicate/combined/malformed credentials are rejected, and source blocks use the existing peer/trusted-proxy policy. The browser Next proxy continues forwarding only the session cookie. It is not a machine credential gateway.

The closed catalog exposes retained account lists/details and account quota observations; participants and scoped pool contracts/evidence; attributed usage captures/view/window/day-or-month history; observation state/history; model state/history; wallet/recommendation receipts; application receipts; and notifications. Their existing domain sections and exported contracts specify exact input/output schemas. For example, POST `/api/v1/accounts/list` takes `{"after":"","search":"","limit":100}`; only the current account scope is queried. Empty grants expose only access/catalog. A read Key cannot call writes even when owned by an administrator. No machine connection/discovery/configuration, native refresh/collection, credential management, arbitrary proxy or combined overview endpoint is provided. Missing facts, partial coverage and null targets retain their original meaning.

Only administrators can issue `management` mode. Its sole additional operation is POST `/api/v1/wallet-applications/request`, with the same actor-scoped `request_id`, current wallet/binding/recommendation references and authorization as the webpage. The current business implementation persists a `rejected` / `not_dispatched` receipt with null target; it makes no native financial call. Catalog availability is `not_dispatched_only`, never financial readiness. The private administrator snapshot includes `actor_api_key_id`; a safe API-Key audit shares the receipt's operation ID, while ordinary summaries keep `details=null`. Read and ordinary Keys are denied before dispatch to this business method. User/request/input deduplication remains unchanged across Keys belonging to that same user.

Defined errors remain safe: 400 rejects malformed input, 401 invalid/revoked/disabled credentials, 403 unsupported machine operations or missing feature/mode (`SOURCE_BLOCKED` for a blocked source), 404 absent or out-of-scope resources, 409 stale revisions/bases, 429 limits and 500 internal failure. A lost create/rotate response leaves its local outcome unknown and its secret unrecoverable. Do not automatically retry; read current metadata and make a deliberate new rotation or revoke. External Sub2API qualification, financial dispatch and public TLS/proxy deployment acceptance remain separate.

The Key page reads all owned metadata pages, up to 2000 records, and the current user's capability catalog. Failed pagination exposes no partial rows; both reads must succeed before lifecycle writes. Generation and rotation display only the server's one-time secret, clear it on close or identity change, and await clipboard success before confirming a copy. Conflicts and uncertain responses preserve feedback and require deliberate metadata readback without automatic replay. Closing a form before a late successful response discards its secret. Grant contraction, logout, owner disable and session expiry invalidate opened content. The original components, styles and light/dark desktop/mobile layouts remain in use. ## Native group pricing reads

The `pricing-v1` contract and `createPricingClient` provide administrator-only POST reads through the shared strict JSON/Origin/cookie boundary. Each input binds the current connection `revision` and `source_id`; configuration locks and final current-session checks prevent stale-source or expired-session results. The existing `/pricing` page reads these group/configuration operations through the same-origin Next proxy. Only current administrators request global connection or pricing data; an ordinary pricing-feature grant does not grant these reads.

| Endpoint | Input | Result |
| --- | --- | --- |
| `/api/v1/pricing/groups` | `revision`, `source_id`, `page`, `search` (at most 100 UTF-8 bytes) | Current visible OpenAI native groups, nullable account counts and explicit pagination/check |
| `/api/v1/pricing/group` | `revision`, `source_id`, `group_id`, `page` | Exact native group identity, current FAST/long-context/base model configuration and independently checked group-associated account page |
| `/api/v1/pricing/default` | `revision`, `source_id`, `model` | Requested model's native default catalog prices in USD per token, explicit found/unknown result and coverage |

IDs and numeric values remain exact strings. Missing group pricing fields appear in `unreported`; they do not become false or zero. Native null model rules mean no group override; a missing model-rules field remains unknown. `projection=base_fields_only` and each rule's `unprojected` fields explicitly exclude interval, time and reasoning rules from interpretation. Group values use `native_config_value` units until the complete native billing semantics are qualified. Default catalog prices exclude reasoning multipliers and do not establish the effective price of a particular request, inheritance across all native layers or historical charges. Account pages require reported native group membership; a visible page does not prove complete shared-group impact or ownership.

These three reads use fixed native GETs with the saved credential and bounded/no-redirect/no-retry transport. Independent denial, malformed response and unknown mode remain visible without exposing raw bodies or secrets. Their original response context retains `can_apply=false`, `write_reason=PRICING_WRITE_UNQUALIFIED`; a read response or standard mode cannot authorize a write. Controlled-operation availability comes from the separate control endpoint below. Reads create no pricing history or financial/notification records.

The shared native transport accepts envelopes only as complete UTF-8 JSON objects with unique top-level keys, canonical lowercase `code`/`data`, integer `code=0` and non-null data. Duplicate keys (including escaped spellings) or control-field case aliases return `INVALID_RESPONSE` without exposing data. An ambiguous HTTP 200 write acknowledgement remains a result to review; it does not prove rejection or permit automatic replay.

The page preserves the supplied selector, cards, model table, editing modal, change cards, confirmation dialog and theme. Complete current-visible pages are required; inconsistent or over-limit lists are discarded (at most 2,000 groups, associations or change records). Native FAST flags, long-context settings and model base-price strings retain false, zero and unknown distinctions. Reloads, selection/source changes and authority loss clear stale protected results; delayed responses cannot restore them. Editing uses the configuration returned with the control fingerprint, preventing a separate stale read from becoming the write basis. The existing FAST multiplier input changes only the reported model-rule FAST multipliers (1–30 existing rules), preserving force/free flags; the model form edits its existing input/output/cache-read fields, and blank clears that override. The API also supports explicit force/free flags and the remaining native scalar price fields. The page has no separate default-catalog lookup or rate-multiplier control; effective prices and complex-rule interpretation remain unqualified.

## Controlled group pricing operations

Pricing writes are disabled by default. Set `SUB_POOL_PRICING_CONTROL_BINDING=<source_id>:<connection_revision>` only for a deployment where one pricing controller is enforced for that exact binding. Changing the saved source or credential revision closes the gate. This setting is an operator prerequisite, not proof of external exclusivity: the native API has no CAS, so an external write between the final read and PUT remains a possible race. Every mutation requires a current browser administrator, a fresh native administrator JWT in standard mode, complete trusted group identity/version/configuration, and explicit acknowledgement of the group-wide impact (including callers outside Sub-Pool). Restricted group-model keys and local machine keys cannot authorize these operations.

| POST endpoint | Behavior |
| --- | --- |
| `/api/v1/pricing/control` | Current source/revision/group-bound availability, fingerprint, safe matching configuration and existing owned operation |
| `/api/v1/pricing/apply` | Caller-known request ID, exact expected fingerprint and 1–30 unique typed FAST/long-context/model scalar changes; save intent and complete sanitized prestate before one native PUT |
| `/api/v1/pricing/operation` | Read a persisted operation by numeric ID |
| `/api/v1/pricing/history` | Source/group-filtered, ascending numeric ID pagination of persisted per-group results |
| `/api/v1/pricing/retry` | Explicit new request ID for an unchanged, known native rejection; recheck the original source/version/fingerprint and never replay an unknown outcome |
| `/api/v1/pricing/revert` | Save a separate intent, verify the last confirmed poststate including native version, restore this owned change's prior values and independently read back |
| `/api/v1/pricing/review` | Explicitly end local custody of a result-unknown operation; retain the unknown native outcome without claiming success or reversal |

Each write must receive a valid native acknowledgement and an independent matching read with a later native version. A timeout, malformed reply, process loss or failed result/audit commit leaves an unknown result; startup/worker recovery never sends the PUT again. Only explicit native 401/403/423 rejections permit a deliberate apply retry. Revert rejection retains the applied operation. Full existing model rules, including intervals and time/reasoning multipliers, are preserved; unknown rule fields close the gate. Values must round-trip through native float64 JSON without changing their canonical decimal text. No local effective-price formula or historical usage/cost rewrite is performed.

`pricing_changes`, `pricing_events` and the shared management journal persist intent/results atomically. One applied or unresolved owned operation per source/group is permitted; combine fields in one intent, then revert or review before creating another. Per-group results are independent, so multiple groups are not atomic. `after_fingerprint` retains the last confirmed applied poststate used for custody, including after reversal; it is not a claim about a later external current state. Business backups include the two pricing tables; active/unresolved custody blocks replacement on either side of restore. Older protected metadata remains readable, while Go still requires an exact compatible schema for restoration. Local simulated acceptance does not qualify an external deployment's exclusivity or production safety.

## Managed accounts and safe observations

The `accounts-v1` contract is in `../contracts/accounts.ts`; `createAccountsClient` shares the validated fixed-origin transport. Every route below uses POST with the strict JSON/Origin/cookie boundary. Adoption, local editing and model reads require a current administrator. List, detail and explicit runtime refresh require the `accounts` read feature and the current local account scope; administrators can read all accounts. Scope filtering happens in PostgreSQL before search and pagination. An absent or out-of-scope detail returns the same 404 without contacting the upstream.

| Endpoint | Input | Result |
| --- | --- | --- |
| `/api/v1/accounts/list` | `after` (empty initially), `search` (literal name substring), `limit` (1–100) | Visible managed accounts and nullable next cursor |
| `/api/v1/accounts/get` | `id` | Local configuration and last safe observation |
| `/api/v1/accounts/adopt` | `source_id`, `connection_revision`, `upstream_id`, `name`, `monitoring`, `source_mode` (`active` or `passive`) | Verified detail read and new local identity; unavailable reads return a safe check with no account |
| `/api/v1/accounts/update` | `id`, `revision`, `name`, `monitoring`, `source_mode` | Persisted local configuration with a new revision |
| `/api/v1/accounts/refresh` | `id`, `revision`, `source_id`, `connection_revision` | Safe runtime read, attempt time and last successful observation time |
| `/api/v1/accounts/models` | `id`, `revision`, `source_id`, `connection_revision` | Readable mapping/passthrough configuration and advisory native model catalog |

Adoption reads the exact upstream identity before creating a random local ID. Source/upstream bindings are immutable. A private fingerprint prevents duplicate OpenAI root resources within a source; shadow accounts never represent independent quota. Restricted or unsupported identities remain explicitly unverified or unsupported. A changed resource identity is quarantined as conflict and cannot silently rebind history. Changing the connection address isolates older accounts, even when returning to a former address. Their history remains readable within the caller's scope.

Local pause, resume, rename and source-mode edits never change upstream scheduling or delete observations. `paused` excludes normal collection. The accounts-v1 `collection_state` is a prerequisite projection; `awaiting_collector` does not describe a live job. Use monitoring-v1 for durable quota jobs and snapshots. The account module's explicit runtime/model reads do not query quota, recover wallets, clear errors or write models/scheduling. Pausing cannot reclaim an upstream balance.

`connection_available` reports configured credential/storage presence, not tested authentication. Each successful snapshot records `observed_connection_revision`. Clearing credentials or losing the storage key produces `connection_unavailable`; replacing configuration at the same address produces `connection_changed` until a successful refresh. Failed refreshes update the safe check and attempt time while preserving the last successful snapshot, its time and its connection revision. Missing runtime fields stay null, real false/zero values remain real, and upstream status is separate from local collection state. All timestamps are UTC. Raw credentials, resource IDs and upstream error text are excluded; only error presence is returned.

Model mappings are configuration, not proof of access or reliable blocking. Missing mapping/passthrough remains unknown; an explicitly empty mapping is not all-disabled. The native catalog may be a fallback, so `access_proven` is always false. Model reads do not change configuration, synchronize models, query quota or refresh tokens. Local writes and audit records commit atomically, use optimistic revisions and recheck authority after waits. Uncertain writes are never automatically replayed.

The existing `/accounts` page and overview read complete, currently scoped account metadata and passive observations through the validated contracts. Cards, tables and drawers keep source measurement, snapshot receipt, metadata observation and latest collection attempt separate. Missing windows and unavailable finance/participant/temporary data stay unknown. Administrators can read advisory model mappings and queue a single-account or collect-all run; ordinary readers receive only their permitted accounts and no global run/model controls. Account grants also populate the existing user-management selector.

Manual collection acknowledges a durable run, then reads its seven possible per-account outcomes until completion. A completed run can contain failures or skips. History and explicit recovery only read stored results; an uncertain submission stays blocked from automatic replay even after a successful read. Process liveness, worker heartbeat, enabled policy and account collection results remain separate health signals. Identity changes invalidate the page state and pending reads. The shared frontend proxy exposes only exact `GET /health` process output, without database or business readiness claims.
